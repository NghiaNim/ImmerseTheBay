## Generated video depth

`ViskoSession.PullFrame` accepts BGRA pixels, uploads them to a Unity texture and assigns it to the feathered stereo shader. There is one generated color view. The fixed eye-level camera, start-image blend and corner captions can remain unchanged in an experiment. XREAL plane, mesh and tracking subsystems describe the wearer's room. A generated shelf needs depth aligned to the pixels in the generated view, with an independent pose and scale. [XREAL feature compatibility](https://docs.xreal.com/XREALDevices/Compatibility) · [Room meshing](https://docs.xreal.com/Depth%20Mesh/NormalMesh)

1. Compare the current flat render, a pair of manually separated static shelf layers, and an offline depth map for the same short clip. Use recorded view motion and review both eyes. Choose images with occlusion edges, lettering and motion near a face if the clip contains a clerk. A useful first layered experiment puts static props behind the existing color surface so the partner and text remain stable. Reproduce each view with head yaw/translation fixed and then with small intentional motion. Judge texture stretching, disocclusion, unstable depth and perceived benefit.
2. Video Depth Anything Small is a reasonable first offline checkpoint. The authors publish an experimental streaming implementation based on temporal-cache reuse and report lower ScanNet accuracy in that mode. The published Small benchmark is 7.5 ms and 6.8 GB VRAM in FP16 on an A100 with a 32-frame 518 × 518 input. The weights have 28.4 million parameters, about 54 MiB at two bytes per parameter before activations, runtime and transfer buffers. The Small license is Apache-2.0. Base and Large model licenses are CC BY-NC 4.0. Confirm the exact weights and runtime rights before deployment. [Official model, streaming notes and licenses](https://github.com/DepthAnything/Video-Depth-Anything#license)
3. Prefer a GPU-hosted experiment if the layered test shows a benefit. Send a small depth map keyed to the exact generated stream epoch and source frame timestamp. A 160 × 90 map at 5–10 Hz costs 72–144 kB/s as R8 or 144–288 kB/s as R16 before encoding and transport. At 640 × 368 and 30 fps, the BGRA color path represents about 28 MB/s of raw pixel data before JNI, Unity and upload copies. Preserve a small latest-only queue. Start with a shallow per-eye displacement cap of 0.5% of the color image width, lower confidence at edges, and flat fallback on stale/missing maps, a cut, uncertain confidence or a discontinuity. Reset temporal state on scene generation changes. Leave the caption and control transforms independent of this displacement.
4. Advance beyond offline only after both eyes look stable on the S25. Proposed gates are p95 added render-thread/GPU time ≤1 ms, p95 depth arrival lag ≤100 ms, no color-frame delay, unchanged missed-frame rate and no sustained thermal regression over a five-minute matched run. Use the actual reported refresh rate and record capture/decode, depth inference, delivery and render timings independently. Require two short wearer A/B passes with no distracting face deformation, double edges, or reported discomfort. Flat rendering stays selected when evidence is missing. The research stage introduced no runtime dependency or model serving.

## Reachable controls and tabletop placement

Existing controls are world-space XRI buttons. The four-button rail uses 206 × 136 UI units per button, 248 units center spacing and world scale 0.00040. That gives approximately 8.2 × 5.4 cm buttons, 1.7 cm horizontal gaps and a 38 cm overall footprint. The fallback center is 48 cm forward and 18 cm below eye height, a look-down angle near 21°. These are code geometry calculations. The example headset needs a wearer to confirm the outer buttons are visible and selectable while seated.

The private `DevLessonControls.PlaceControls()` raycasts within a tracked horizontal-up plane and accepts a hit ≤1.1 m away and 0.12–0.65 m below eyes. At this baseline it has no tracked caller, and `placementStatus` is set without a displayed consumer. `LearningOverlay` stores a pose override until it is replaced, with no tracking-aware revalidation. Reconnect and fresh-run behavior need explicit handling before relying on a placed rail. `LearningContext.HasDeskPlane` uses a different 0.6–0.9 m below-head heuristic for agent context. Seated and standing height tests should evaluate these thresholds independently and align intent where they overlap.

- Air 2 Ultra supports plane tracking, room mesh and spatial anchors. The locally installed 3.1 plane descriptor advertises horizontal and vertical planes and boundary vertices. The SDK's distinct mesh classification path includes TABLE labels. Existing `LearningContext` obtains mesh face classifications with an active XREAL loader and a running mesh subsystem, and falls back to known geometry when unavailable. Treat a confirmed, tracked horizontal plane as sufficient for placement. A TABLE mesh label can rank hits when available. [XREAL plane detection](https://docs.xreal.com/Plane%20Detection/) · [XREAL mesh capabilities](https://docs.xreal.com/Depth%20Mesh/NormalMesh#capabilities) · [AR Foundation 6.1 ray casts](https://docs.unity3d.com/Packages/com.unity.xr.arfoundation@6.1/manual/features/raycasts.html)
- First wire explicit phone Place and Reset actions and a transient hit preview. Reject subsumed planes and require adequate polygon clearance for the whole rail, at a reach the seated learner confirms. Prefer a visible smaller rail or two-button row on narrower surfaces. Record the accepted trackable ID, retest it on rebase/reconnect and honor the saved placement as long as it stays valid. On loss, suspend press and return deliberately to the existing fallback or phone. A tracked pose is sufficient for an in-run experiment. Consider `ARAnchorManager` only if drift measurements justify it or the product requires placement across sessions. [XREAL spatial anchors](https://docs.xreal.com/Spatial%20Anchor/intro)
- Test a single extruded Speak target behind a development setting. Validate its visual hover and roughly 4–6 mm press travel using XRI's existing poke interactor/filter. Keep one action handler shared with tested UI and phone touch. Use explicit release to rearm, cancel on tracking loss, and verify simultaneous near/far selection cannot trigger a duplicate. Keep the camera/head pose fixed during a press. Preserve controller and pinch access, while native phone controls provide recovery. [XRI 3.0 XR Poke Interactor](https://docs.unity3d.com/Packages/com.unity.xr.interaction.toolkit@3.0/manual/xr-poke-interactor.html) · [XRI 3.0 XR Poke Filter](https://docs.unity3d.com/Packages/com.unity.xr.interaction.toolkit@3.0/manual/xr-poke-filter.html)
- Compare existing and candidate controls across 20 trials per modality (left hand, right hand, phone) using the same chair, table and task order. Measure first-click success, accidental activations and p50/p95 time-to-select. Include a floor/wall false-positive test, dark or glossy table, temporary occlusion, recenter and wire reconnect. Proposed gates are ≥95% first-click success per modality, zero duplicate activations, seated reach without leaning off the chair, and p50 selection no slower than baseline. Placement drift target is ≤2 cm over the three-stage lesson. Keep table placement and poke deployment settings independent so either can be disabled.

## Representative scene thumbnails

`portal/records/recorder.js` records a committed turn keyed to a run along with the presented and practiced target IDs. `compile.js` projects the event log by target ID into saved Review. A score `attemptId` belongs to the previous target. Bind a thumb to the newly presented target and its presentation revision, whose reliable persisted association is a prerequisite for this feature.

1. Use the key `{runId, targetId, presentationRevision, mediaEpoch, sceneId}`. Record `presentationRevision` and `sceneId` from the committed response alongside `presentedTargetId`. A target may be seen again after a detour. Keep the first qualified capture for `(runId,targetId)` and preserve the recorded revision, or leave it missing until a later qualified presentation. Use a server-minted opaque ID for the file path, with owner checked through the saved run lookup. Retries reuse the key, and different targets with identical sentence text retain distinct keys.
2. At Unity's target-presented event, schedule at most one capture after native has accepted a frame for the exact transport/scene generation, and presentation is still current. A command ACK or local increasing frame counter alone cannot establish generation identity across reset. Increment/clear the media epoch at reset, Leave, connection adoption or transport loss. Drop stale captures after a newer presentation, run exit, rapid Next or Cancel. Recheck on GPU callback, before upload, and against recorded presentation on the server. If identity is ambiguous, omit the image. Use decoded color only, cropped with the same geometry and vertical orientation as the learner view. Provide the corresponding allowlisted start image with the label “Scene preview” when no valid capture exists. [Existing native boundary](IMPLEMENT-demo-video-lookahead.md#measurements-and-failure-checks)
3. Blit the cropped color texture into a reusable 320 × 180 target, asynchronously read it back only if the runtime reports support, and send the pixels to one worker for JPEG encoding. Use a generation token and main-thread callback drain. Dispose arrays/textures only when ownership ends. The thread-safe array JPEG encoder can run outside the render-critical path. Measure its memory copies and avoid an every-frame GPU readback or synchronous screenshot. [Unity 6 AsyncGPUReadback](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Rendering.AsyncGPUReadback.html) · [Unity 6 JPEG array encoding](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/ImageConversion.EncodeArrayToJPG.html)
4. For the prototype cap each sanitized JPEG at 48 KiB and each run at 12 thumbnails (576 KiB maximum encoded cache). Keep binary assets alongside the run, serve lazily through owner-scoped routes, and expose only an opaque ID with an optional immutable source digest in Review. Make delete and write atomic relative to each other so a late request cannot recreate a deleted run. A timed-out/rejected thumbnail encoding or upload leaves text and audio available. Avoid raw photo bytes, arbitrary video segments, and a new indefinite storage promise for temporary photo-based lessons. Limit initial capture to authored scenes. Extend to real-world photo-derived frames only with clear opt-in, published retention, deletion and cache invalidation. Existing temporary photo practice has a 30-minute memory-only window. [Existing photo policy](../../portal/practice/README.md)
5. Desktop size timing used Python Pillow 13.0.0 on Mac16,8 ARM64 and the three tracked 1672 × 941 reference images. Decode each PNG once, use `ImageOps.fit` with bilinear filtering for 320 × 180, and JPEG quality 75 in memory with empty EXIF. One warmup then 60 repetitions per image gave 12,978–14,627 bytes and p50 5.415 ms / p95 5.898 ms across 180 resizes and encodes. Three encoded stills totaled 40,661 bytes. This measures a desktop proxy with predecoded source stills. Unity GPU transfer, S25 Android scheduling and noisy live-frame byte sizes require separate measurement.
6. Promote only after frame identity passes rapid Next, same-scene advance, detour/rejoin, video delay, two same-text targets, run replay after restart, and delete-during-capture. Measure baseline render and capture-on runtime p95 frame time with a proposed ≤1 ms render-thread difference, one in-flight capture and zero visibly dropped frames during target reveal. Add service tests for ownership, exact event association, duplicate uploads, MIME and bounds, deleting runs, and missing legacy assets. Evaluate the images in both practice detail and saved Review on the same run.
